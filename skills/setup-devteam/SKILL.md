# setup-devteam

devteam 的角色只寫通用的做法，專案的事實由契約提供。契約是一組檔與節，清單與每一節要寫到什麼程度在 [`contract.md`](contract.md)；先讀完它再開始。

契約裡的事實分兩種：**推得出的**（指令、路徑、標籤、分支慣例、合併方式）從 repo 與 GitHub 查，**要決定的**（使用者是誰、哪些畫面要量、開票門檻、誰能合併）只有使用者能定。推得出的不拿去問他；證據互相矛盾時，就變成要決定的。

## 1. 盤點

先 `git fetch`，記下盤點的基準 commit，並看 `git status`。

照 `contract.md` 每一節的「從哪裡查」去讀：既有的 `AGENTS.md`／`CLAUDE.md`、`CONTEXT.md`、`docs/agents/`、套件與建置設定的 scripts、CI workflow、PR 範本、`gh label list`、repo 設定與主線的保護規則、最近合併的 PR 與 commit、最近關閉的票、畫面與樣式檔、測試目錄。

也盤點 repo 自己的 `.claude/agents/` 與 `.claude/skills/`：與 devteam 角色做同一件事的（例如 repo 自己的 `qa`），列一列「要決定」問留著或併進 devteam，並 `grep` 出引用它的檔（指南、skill 的 description），決定移除時一起改。

做一張盤點表，**一個事實一列**，同一節的列排在一起：

| 檔〈節〉 | 事實或題目 | 狀態 | 依據 |
| --- | --- | --- | --- |
| `dev-workflow.md`〈指令〉 | 結束前的全套含整合測試 | 推得出 | `.github/workflows/phpunit.yml:31` |
| `dev-workflow.md`〈畫面〉 | 要量哪些寬度 | 要決定 | 斷點：`src/views/Detail.vue:1195` 的 1023px |
| `issue-tracker.md`〈Definition of Done〉 | 驗收區的標題 | 要決定 | 已關閉的票有四種寫法：`gh issue list` 統計 |

狀態五種：

- **已有**：檔裡寫了，而且與現況相符。
- **不符**：檔裡寫了，但與現況不符；依據欄寫兩邊。
- **推得出**：還沒寫，repo 或 GitHub 查得到唯一的答案。
- **要決定**：沒有證據、證據互相矛盾（例如最近的寫法有好幾種，或 repo 的慣例與某份文件不同），或屬於 `contract.md` 列的「要問使用者的」。推得出卻仍要使用者確認的，推出來的答案就是推薦選項。
- **不適用**：專案沒有那件事（例如沒有畫面就沒有〈畫面〉），寫理由。

**完成條件**：表的開頭寫了基準 commit 與工作區是否乾淨；`contract.md` 的每一節至少一列；「已有」「不符」「推得出」都附檔案:行號或指令與輸出。

## 2. 問

把盤點表給使用者看，再用 `AskUserQuestion` 問「要決定」的列：一次最多三題，每題 2～3 個選項，推薦的放第一並標「（推薦）」，description 寫選了之後角色會怎麼做、代價是什麼。推薦照 `devteam:team`〈推薦選項的判準〉；有 `defaults/` 可用時，「採用預設」是其中一個選項。

順序：先問會改變其他題目的（使用者是誰、停點、誰能合併、要不要實機驗收），再按檔問其餘的；前面的答案改變了後面題目的意思或代價時，照答案改寫那一題再問。「不符」的列問要改成現況，還是現況才是錯的。推薦明顯、代價小的幾列併成一題「全部照推薦」，選項列出每一條，使用者要改哪條再單獨問。

使用者在「推得出」的列指出錯誤時，回第 1 步重查那一列，不照他的說法直接改。

**完成條件**：表上沒有「要決定」與「不符」的列，每一題都有使用者的答案。

## 3. 寫

工作區有不屬於這次的未提交改動時，先問使用者再寫。

- 照 `contract.md` 的節名寫，`docs/agents/` 底下的節名一字不差：角色以「檔名〈節名〉」找它。
- 權威已經在別處的（套件的 scripts、`AGENTS.md` 的規則、`docs/guides/` 的指南、repo 自己的 skill），寫指向它的一句，不抄內容。
- 每條一句規則加短理由，不寫盤點經過與會飄移的數量。
- 既有檔只補缺的節、改「不符」的地方；契約以外的內容與契約以外的檔保留不動。
- 採用預設的節，從 `defaults/` 複製後把通用的說法換成這個專案的（「使用者」換成真實的身分、例子換成這個 repo 的工具），填好之後刪掉預設裡的 HTML 註解。

**完成條件**：盤點表的每一列都落在檔裡（不適用的除外），`docs/agents/` 的節名與 `contract.md` 相同。

## 4. 驗

- **指令**：〈指令〉與〈這個 repo 的指令〉列的每一條實際跑一次，記下結束碼與結論行；文件為主 checkout 與 worktree 各寫了一種跑法時，兩種都跑。跑不了的（需要服務、帳號或很久）在報告標明沒跑與原因。
- **路徑**：契約提到的每個檔與目錄都存在。
- **節名**：`grep '^#' docs/agents/*.md`，與 `contract.md` 的節名逐一比對。
- **角色讀得到**：派 `devteam:pm` 一句話任務：「讀 devteam:team〈專案契約〉，逐檔逐節回報這個 repo 缺什麼，不做其他事。」它回報缺的只能是「不適用」的那幾節。

**完成條件**：四項都有結果；跑失敗的指令與缺的節已修好或寫進報告。

## 5. 回報

寫了或改了哪幾個檔、每一節的事實來源（推得出／使用者決定／預設）、跑過的指令與結果、沒跑的與原因。不 commit：問使用者要不要提交與開 PR。
