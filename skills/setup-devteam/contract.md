# 專案契約

角色以「檔名〈節名〉」引用 `docs/agents/` 底下的節，節名一字不差。每一節寫：**要有什麼**（角色拿它做什麼）、**從哪裡查**、**要問使用者的**。標「選用」的節，專案沒有那件事就不寫。

通用的處理方式：

- **既有文件已經寫了某節的內容**（例如 repo 自己的 skill、代理或指南）：那一節寫一句指向它，不重寫。
- **團隊慣例與個人慣例**：契約寫的是團隊的做法。只有某位維護者自己的做法（例如分支前綴用他的名字）寫成通則（`<開分支的人>/…`），個人慣例留在他自己的設定。
- **CI 跑的與擋合併的不同**：〈指令〉的全套以 PR 上 CI 實際跑的全部檢查為準，不只看擋合併的必要檢查；角色開 PR 前要它們全綠。

## `AGENTS.md`

每個 session 都會載入，不需要固定節名，寫成一句認得出來的規則即可。

- **要有什麼**：產品的使用者是誰（角色講「使用者體驗」時指的對象，不含維護者）；只有使用者能決定、角色要停下來問的事，在 `devteam:team` 的兩件之外還有時列出；一行指向 `docs/agents/` 整個目錄。
- **從哪裡查**：README、既有的 `AGENTS.md`／`CLAUDE.md`、產品畫面的文案、部署 workflow（合併就部署到哪裡）。
- **要問使用者的**：使用者是誰（推得出時請他確認）；有沒有別的停點（例如合併就部署到某個環境、碰正式資料、對外寄信）。

## `CONTEXT.md`（選用）

詞彙表。沒有時不在這裡建：角色遇到缺口會交給 `domain-modeling`。

## `docs/agents/issue-tracker.md`

- **讀寫票的指令**（不限節名）：讀、列、建、留言、改標籤、關票的 `gh` 指令。tracker 不是 GitHub Issues 時寫該工具的對應指令。
- **〈什麼該變成票〉**：審查與實作途中的發現什麼時候當場修、什麼時候開票、什麼時候不記。從哪裡查：既有文件有沒有相關規定（例如舊程式只修某幾類缺陷、其餘記到某張票），有就在這一節指向它。要問：是否採用 `defaults/tickets.md`。
- **〈Definition of Done〉**：合併後怎麼收票。從哪裡查：最近關閉的票，驗收 checkbox 寫在哪個標題底下；最近合併的 PR 有沒有用 `Closes` 自動關票；PR 範本有沒有別的追蹤系統（例如 Jira）要同步，實際上有沒有在填。要問：是否採用 `defaults/tickets.md` 的流程；驗收區標題不只一種時，角色要認哪幾種、新票統一用哪一種；別的追蹤系統由誰同步。

## `docs/agents/triage-labels.md`

- **要有什麼**：類別（`bug`、`enhancement`）與狀態（`needs-triage`、`needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix`）在這個 tracker 的標籤字串；有接手（`in-progress`）、等外部（`waiting-upstream`）這類手動維護的標籤時也列出。triage 用不到的其他標籤不列。
- **從哪裡查**：`gh label list`。
- **要問使用者的**：缺的標籤要不要建（建標籤是對外的寫入，等他同意）；不建接手標籤時，接手改用 assignee 表示。

## `docs/agents/dev-workflow.md`

- **〈指令〉**：邊做邊驗（型別檢查、單跑一支測試）與結束前的全套。從哪裡查：套件與建置設定的 scripts、CI workflow 的每個 job。檢查要在容器或特定環境跑時，寫在哪裡跑、worktree 裡怎麼跑。
- **〈分支、commit 與合併〉**：分支命名、commit 格式、跟上主線的方式、開 PR 的指令與範本、合併指令、合併之後發生什麼（部署）與要做什麼（更新主 checkout、重裝相依）。從哪裡查：最近合併的 PR 的分支名、`git log` 的 commit 格式、repo 設定允許的合併方式、主線保護規則、部署 workflow。要問：誰能合併；沒有核准時能不能略過審核；要不要讓 autopilot 合併時不被權限提示擋（在 repo 的 `.claude/settings.json` 允許 `gh pr merge`）。
- **〈畫面〉**（選用：有使用者介面才寫）：哪些路徑算畫面（`rd` 依此決定派不派 `uiux`）、共用樣式的權威（元件庫、版面類別、色彩與尺寸變數）、斷點、點擊範圍下限、外觀基調、要量的寬度與配色及量不完時的優先順序、怎麼起一份服務與截圖。從哪裡查：前端目錄、所有樣式（含元件內的 `<style>`）的 `@media` 與 `prefers-color-scheme`、元件庫的相依。要問：要量哪些寬度、有沒有深色模式要量、外觀基調與點擊下限要另訂或沿用元件庫。
- **〈實機驗收〉**（選用：有這一節就是交付前必做）：什麼改動要做、用哪個 skill 或步驟、派工要明示的範圍（可以寫入什麼、能不能寄信、能不能停共用服務）、報告放在哪裡。從哪裡查：repo 裡有沒有驗收用的 skill、代理或腳本。要問：要不要實機驗收、哪些改動要做。

## `docs/agents/testing.md`

- **〈六條門檻〉、〈第 5 條：反向驗證怎麼做〉、〈docstring 寫什麼〉**：判斷一支測試值不值得留、怎麼證明它不是空殼。要問：是否採用 `defaults/testing.md`；repo 既有的測試規則與預設衝突的地方（例如規定要以真的套件執行某段邏輯，與第 3 條「不測不是我們寫的東西」）以哪一邊為準。
- **〈這個 repo 的指令〉**（〈第 5 條〉底下的小節）：單跑一支、全套、注入缺陷的工具；沒有突變測試工具時寫手工注入與自動還原的做法。從哪裡查：測試 runner 的設定與 scripts。
- **〈測試分層〉**：每一層測什麼、用真的還是假的相依、哪些故障只有實機看得到。從哪裡查：測試目錄的結構、既有測試怎麼換掉資料庫、網路與外部服務；repo 已有測試規則時指向它。
